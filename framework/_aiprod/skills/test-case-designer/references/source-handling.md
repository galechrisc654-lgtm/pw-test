## 最小信息标准

不要根据资料的形式判断信息是否充分。应将所有资料统一整理为测试设计依据。

整体上必须明确：

- 测试目标：本次验证哪个功能或变化。
- 测试范围：包含哪些核心行为、结果和必要回归，排除哪些相邻功能；否定规则较多时，还包括负向覆盖方式。
- 需求基准：什么内容用于判断正确行为。

每个核心行为必须能够形成业务层可执行闭环：

- 测试对象：被验证的功能、业务对象或状态变化。
- `Given`：影响结果的角色、上下文、状态、配置或数据。
- `When`：一个主要的用户或系统动作。
- `Then`：有需求依据、可观察且可判定的结果，包括必要的数据、状态、关联结果和失败副作用。

准入目标是足以设计用例，不是完成测试实施准备。执行者可以具备系统基本操作知识，但不得自行补充产品规则、选择冲突口径或猜测预期。需求给出明确约束时，可以据此构造代表值和边界值。

以下内容属于执行准备，缺失时本身不阻断准入：

- 精确菜单路径、按钮位置和自动化定位器；
- 真实账号、测试环境和测试数据创建方式；
- SQL、接口地址、多账号同时操作或模拟异常的方法；
- 非核心提示文案、排序、截断方式和视觉布局。

对于重复提交或重复处理、多人或多请求同时操作，以及批量或联动操作中途失败等场景，只要触发条件、业务动作和预期结果明确，就可以设计用例并说明执行依赖。只有缺口导致核心测试对象、主要动作或唯一结果无法确定时，才阻断准入；局部非核心缺失只影响对应断言或用例。

## 准入状态

### Ready

同时满足：

- 测试范围只有一种合理解释；
- 核心行为达到上述最小信息标准；
- 需求基准可识别；
- 没有会改变重要用例或唯一结果的未解决冲突。

### Scope Unclear

测试范围存在两个以上合理解释，而且不同解释会显著改变用例数量、覆盖内容或设计深度。例如，资料同时涉及新建、查询、下游结果和其他角色能力，却无法判断它们属于核心测试、结果观察还是范围外内容。

若输入资料含有较多“不允许、不得、阻断、只允许”等明确规定的限制与失败规则，逐条展开预计会让相关用例接近总量三分之一或明显扩大产出，而用户尚未指定覆盖方式，也属于范围不明确。提供两个选择：

1. `仅正向`：只设计成功路径和正向业务分支，明确规定但未覆盖的限制与失败规则列入未覆盖说明。
2. `正向 + 输入资料中明确规定的限制与失败场景`：覆盖输入资料明确规定的限制与失败行为，但不扩展经验推断的场景。

少量已明确规定的规则默认采用第二种方式，不为此单独打断用户。这里的输入资料必须能够作为需求基准；代码、开发概述等实现参考不能单独作为业务预期的依据。

不要根据目录、文档数量或代码改动自行扩大范围。先说明建议覆盖和排除的内容，再请用户确认或调整。

### Missing

缺少形成范围或核心行为闭环的信息，例如：

- 只有功能名称、代码目录或“测试当前改动”，没有明确业务目标；
- 有字段或操作，但没有关键条件、规则或结果；
- 新增能力只出现在修改记录中，没有完整定义；
- 关键链接、截图或附件不可读取，且其中内容影响核心行为；
- 无法从需求基准确定唯一 `Then`。

不要仅因缺少执行环境、账号、数据创建方式、接口地址或测试工具而判为 `Missing`。

### Conflict

资料对同一对象、范围、规则或结果存在不同定义，并会产生不同用例或预期。例如对象名称无法确认是否相同、需求与产品事实不一致，或不同章节定义互斥规则。

代码与需求基准、产品说明或已确认交互明显不一致，也按 `Conflict` 处理，但代码只占“实现现状”一侧，不自动成为候选需求基准。冲突必须拆成可独立决定的业务规则、分支或结果；同一功能中允许一部分接受实现、一部分继续坚持原要求。

## 交互与资料补充

### 输出位置确认

在收集资料时同步确定输出位置，不把它设为任务开始后的固定交互步骤：

- 用户已指定目录时直接采用；用户指定文件时使用其所在目录，测试用例统一命名为 `test-cases.md`。
- 能唯一识别当前项目、用户未指定位置且当前环境允许写入时，直接使用项目根目录，不询问默认位置。
- 当前环境限制写入默认位置、没有当前项目、存在多个项目或路径归属不清时，请用户指定或确认目录或文件，未取得位置前不生成用例。`test-cases.md` 已存在时按下文规则处理。
- 测试用例文件名固定为 `test-cases.md`。目标目录已有该文件且用户未要求覆盖时，请用户确认覆盖、指定其他目录或合并更新；不得以其他文件名规避冲突。
- 输出位置不参与 `Ready` 判断。

优先使用可点击的结构化选项；不可用时提供等价的编号选项。用户始终可以直接输入路径。

### 交互方式

先判断当前 Agent 或宿主环境是否提供结构化交互工具：

- 支持时，对是否继续、范围选择、冲突结论等有限且互斥的确认，优先提供 2～3 个可点击选项，并保留自由输入入口；将建议选项放在首位并简要说明影响。
- 不支持时，使用内容等价的编号选项或简短问题，允许用户直接回复编号或自行说明。
- 对业务规则、矛盾原因、文件路径、链接和附件等开放信息，始终允许用户自由输入，不强制转换为选项。
- 不得假设交互工具存在，也不得因无法展示按钮、文件选择器或多选控件而暂停任务。

单个问题能够表达清楚时不要拆成多个交互步骤。多个问题互相依赖时逐个确认；互不依赖时可以在同一轮提出，但仍遵守每轮不超过三个高影响问题。

### 资料不足时的必要澄清

状态不是 `Ready` 时，不生成完整用例。每轮提出不超过三个问题，按范围、核心结果、冲突、关键规则的顺序处理。

每个问题说明：

- 发现的缺失、歧义或冲突；
- 它会影响哪些范围、场景或预期；
- 需要用户补充什么，或在什么选项中确认。

代码冲突优先使用结构化清单一次报告给产品负责人，每项包含：

- 稳定的冲突编号和业务主题；
- 需求基准或产品资料定义的预期；
- 代码表现出的当前行为及文件、函数或调用链证据；
- 受影响的测试范围、用例或预期；
- 建议处理及理由；
- 产品负责人决定：`保留需求基准`、`接受实现现状`、`拆分后分别决定` 或 `暂不决定`。

产品负责人选择“接受实现现状”时，其明确回复可作为本次需求说明，但必须在测试依据中记录，不能只修改用例而不留下新的基准。选择“保留需求基准”时，继续按原预期编写用例，并把代码差异保留为实现偏差，不为使当前实现通过而降低预期。选择“暂不决定”时，仅省略或标记受影响用例；其余已闭环内容可继续。

如果补充资料能直接解决缺口，应同时说明用户可以提供哪些需求、产品、原型、接口、数据样例或实现资料，以及这些资料能够补足什么；不要脱离当前缺口泛泛索要更多资料。

用户回答后重新判断状态，直到 `Ready`。用户可以明确要求只生成已闭环部分；此时省略未闭环场景或标记待确认，不得选择冲突标准或编造结果。

## 资料角色

### 需求基准

正式需求、验收标准、用户明确确认的需求说明和适用于本次范围的正式产品规则，用于确定测试范围、业务规则和预期结果。没有需求基准时不能通过准入。

### 产品背景

产品文档用于理解未被本次需求修改的已有行为和必要回归。只读取与本次范围相关的部分。

### 表现资料

原型、设计稿、截图和交互说明用于理解入口、字段、控件、操作顺序和反馈形式，不能独立决定业务规则和数据结果。

### 实现参考

开发概述、代码、Git diff、接口和数据库改动只用于定位实现入口、实际动作和观察位置，不能决定测试范围、需求基准或唯一预期。

功能或交互资料可以证明页面入口、控件和展示行为；数据对象资料只能证明字段语义、关系和数据结果。不要因为数据对象存在某字段，就推断页面必然展示该字段。

## 代码使用

测试范围尚未 `Ready` 时，不通过扫描代码自行确定范围。只有用户明确要求结合实现，或代码能够细化已闭环场景的入口、字段、参数和观察位置时才读取。

优先读取用户提供的开发概述、diff、提交和相关文件，不对整个仓库做无边界分析。开发概述足以细化动作时，不继续读取完整代码。

不得根据代码：

- 补充产品未定义的规则；
- 扩大测试范围或新增回归目标；
- 判断未写入需求的默认值、限制或异常行为是否正确；
- 将当前实现作为唯一正确预期。

为细化操作而读取代码时，如果发现代码与需求基准明显不一致，应按本文件的冲突清单报告产品负责人，但不自行延伸为完整代码评审或确定缺陷。只有产品负责人决定保留需求基准后，该差异才可作为实现偏差交给后续实现核查或缺陷流程；决定接受实现现状时，先记录新的需求基准，再据此设计用例。

## 资料获取与异常处理

可接收自然语言说明、附件、文件、目录、仓库、分支、提交或链接，不要求固定的 JSON、YAML 或目录结构。只在用户指定范围或当前工作区内查找资料，不无边界扫描其他目录。

失效链接、无法识别的颜色引用、缺失截图、疑似错字和重复字段不能自行还原。它们影响范围、规则或唯一结果时，状态为 `Missing` 或 `Conflict`。

需求明确修改已有行为时，以已确认的新行为为目标，旧行为只用于分析影响和必要回归。原型、产品文档、用户说明或实现参考相互不一致时，不自行选择；说明差异和影响，请用户确认。

所有最终采用的依据应在测试用例文档中列明。代码和开发概述标注为实现参考，不作为需求基准。
