# 测试用例文档模板

使用以下结构生成一份 Markdown 文档。删除不适用的可选章节，不保留说明性占位文字。

编写时保留第 5 节“质量与执行评估”及其全部小节、字段和表头，字段值和表格数据行留空，不填写模板中的枚举、占位值或示例行；评审内容由后续独立评审写入。

```markdown
# {需求名称}测试用例

> 审核状态：待审核  
> 生成日期：{YYYY-MM-DD}

## 1. 测试范围

### 1.1 本次覆盖

{说明本次需求变化、覆盖功能和需要验证的主要业务结果。}

### 1.2 不在本次范围

{说明明确排除或与本次变化无直接关系的内容。没有时删除本节。}

- {需求、验收标准，或用户已明确确认的需求说明}

### 2.2 产品与交互参考

- {产品文档、原型、截图或接口说明。没有时删除本节。}

### 2.3 实现参考

- {代码目录、分支、提交、diff 或开发概述}
- 说明：实现参考只用于细化测试入口、动作和观察位置，不作为需求基准，也不用于扩大测试范围或确定预期结果。

## 3. 通用前置条件

- {多个用例共享的环境、角色、配置和基础数据。没有时删除本节。}

## 4. 测试用例
```

## 输出规则

- 标题和审核状态必须明确表明这是待用户审核的测试用例文档。
- “测试依据”必须区分需求基准和实现参考。
- 没有实现改动输入时删除“实现参考”，不要制造“未提供代码”的噪声；仅在缺失确实影响用例时写入未覆盖说明。
- 没有待确认问题或未覆盖内容时删除相应章节。
- “资料与实现冲突”只保留尚未决定的逐项冲突。产品负责人接受实现现状后，将其明确决定写入“需求基准”；保留原要求时，用例继续采用原预期，代码差异不改写为需求依据。
- 需要确认的预期统一放在“待确认问题”，不要改称“待审核关注点”，也不要同时把推断写成确定预期。
- 除非用户明确要求，不新增“临时试用”“不构成正式资料”等模板之外的产出声明。
- 按实际功能或业务结构分类，不强制使用固定的“正常、异常、权限”分类。
- 每条用例的优先级、前置条件和测试数据使用无序列表；前置条件或测试数据包含多项时使用嵌套列表，不使用两列表格或带圈序号压缩成长段文字。
- 编写时“质量与执行评估”的字段值和表格数据行留空，不以“无”、零值或待评审等文字代替空白；不执行该节的评估或评分。
- 完成后的文档保存到任务开始时确定的位置；对话默认只返回文件位置和摘要，不重复输出完整正文。
- 最终文档只包含测试设计，不包含实际执行结果、缺陷结论或上线意见。
