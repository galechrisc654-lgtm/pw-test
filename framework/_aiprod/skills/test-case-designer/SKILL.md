# 测试用例设计

## 目标

将形式和完整程度各异的需求资料转换为测试用例文档。先按统一的准入标准判断资料是否足以支持用例设计，必要时与用户澄清；准入后围绕本次变更设计最小充分的用例，不依赖特定产品框架或目录结构。

## 工作边界

- 只设计和编写测试用例文档。
- 不评审或评分测试用例，不执行测试、不准备真实测试数据、不生成自动化脚本、不记录缺陷、不判断能否上线。
- 不主动读取已有测试用例、自动化测试、历史测试报告或历史缺陷。
- 将实际开发改动作为实现参考，只用于细化测试入口、操作和观察位置；不得用它决定测试范围、需求基准或预期结果。发现实现与需求基准、产品说明或已确认交互明显冲突时，必须按冲突项报告产品负责人并等待逐项决定，不得整体默认采用代码现状。
- 遵守目标工作区中的本地规则，但不得假设任何固定框架结构或目录存在。

## 核心流程

### 1. 确定输出位置并收集资料

开始处理需求时确定文档保存位置：

- 用户已指定目录时直接采用；用户指定文件时使用其所在目录。测试用例文件名固定为 `test-cases.md`。
- 能唯一识别当前项目、用户未指定位置且当前环境允许写入时，直接在项目根目录生成 `test-cases.md`，不为默认位置单独询问。
- 当前环境限制写入默认位置、无法识别当前项目、存在多个候选项目或路径归属不清时，才请用户指定或确认目录或文件；位置确定前不生成用例。`test-cases.md` 已存在时按后文规则处理。

位置选择遵循 [资料处理规则](references/source-handling.md) 的交互方式，但不属于资料准入。

随后优先使用用户已提供的自然语言、附件、文件、目录、仓库或链接，不重复询问已经明确的信息。

至少需要一项可作为需求基准：正式需求或验收标准，或者用户明确确认的需求说明。按需接收产品文档、原型、截图、接口说明、数据样例和实际开发改动。

### 2. 执行准入检查和必要澄清

将输入统一映射为测试目标、包含与排除范围、需求基准，以及核心行为的测试对象、关键条件、动作和可判定结果。按 [资料处理规则](references/source-handling.md) 判断：

- `Ready`：范围能够唯一确定，核心行为形成业务层可执行闭环，且无关键冲突。
- `Scope Unclear`：存在两个以上会改变重要用例的合理范围解释。
- `Missing`：缺少形成测试目标、条件、动作或唯一结果所需的信息。
- `Conflict`：资料对范围、规则或结果存在不一致定义。

当输入资料包含较多限制或失败规则，且是否覆盖这些规则会明显改变用例数量时，请用户在“仅正向”和“正向 + 输入资料中明确规定的限制与失败场景”之间选择。少量已明确规定的规则默认覆盖，不另行确认。

代码冲突按可独立决定的业务规则、分支或结果拆分，不把多个差异合并成一次“是否以代码为准”的总确认。每项须说明资料预期、代码现状、证据、影响的用例和建议处理。产品负责人可分别选择保留需求基准、接受实现现状、部分接受后继续拆分，或暂不决定；接受实现现状只有在该决定被明确记录为本次需求基准后才能改变用例预期。未决定项只阻断受影响用例，不阻断无关且已闭环的范围。

状态不是 `Ready` 时，每轮优先提出不超过三个高影响问题，等待用户回答后重新检查；默认不生成完整用例。只有用户明确要求按已确定部分继续时，才省略或标记未闭环场景，不得自行补全。

澄清时说明用户可以补充与缺口直接相关的需求、产品、原型、接口、数据样例或实现资料，以及它们能够改善的范围、动作或预期；不要为资料补充另设固定暂停步骤。

准入只要求资料足以设计业务层可执行用例，不要求用户预先解决账号、环境、数据创建、接口地址、多账号同时操作或模拟异常所需的工具等执行准备。局部非核心细节缺失不得阻断整体准入。

需要用户选择或确认时，若当前环境提供结构化交互工具，则优先使用可点击选项；不可用时自动改用编号对话，不得因此中断流程。详细交互规则见 [资料处理规则](references/source-handling.md)。

### 3. 设计最小充分用例

提取本次新增、修改、取消、业务规则和验收结果，确定直接测试及由需求基准证明的必要回归范围。避免扩展到无直接关系的完整模块测试。

优先覆盖核心成功场景、明确的拒绝场景、关键分支，以及重要的数据或状态结果。边界、权限、接口异常、多人或多请求同时操作、性能、安全和兼容性等内容，仅在需求基准或产品背景明确涉及且有实际价值时加入。先按 [用例设计规则](references/case-design-rules.md) 形成内部场景选择清单，决定哪些场景独立成例、并入其他用例或排除，再对候选用例执行轻量 Given–When–Then 检查，并根据现有资料尽量写得具体。

### 4. 形成文档并交付

按 [用例设计规则](references/case-design-rules.md) 完成基本编写自检，使用 [输出模板](references/output-template.md) 形成完整文档：

- 将文档写入第 1 步确定的位置，文件名固定为 `test-cases.md`。
- 目标文件已存在且用户未要求覆盖时，不得以其他文件名另存；说明已有用例文件并请求用户确认覆盖、指定其他目录或合并更新。
- 文档必须标记“审核状态：待审核”。
- 只有用户明确审核同意后，Agent 才可在同一文件中将其更新为“审核状态：已审核”；提出修改意见、补充资料或仅确认已收到均不视为审核通过。
- 保留模板第 5 节“质量与执行评估”及其全部小节、字段和表头；字段值和表格数据行留空，不填写结论、分数、数量、难度等级、“无”或说明性占位文字，交由后续独立评审填写。
- 本 Skill 不执行质量评估、可执行性评分、执行准备难度分级或复评，也不自动调用评审 Skill。

交付时简要说明文档位置、主要覆盖范围和待确认问题，不重复粘贴完整文档，除非用户明确要求；不声称测试已经执行或可以上线。
