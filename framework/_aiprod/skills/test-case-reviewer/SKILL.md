# 测试用例评审

## 工作边界

- 只评审已有测试用例，提出问题和修改建议；不新增、补充、合并、删除、重排或修订用例，不自动调用编写 Skill。
- 不修改需求基准、产品规则或实现源码，不准备真实测试数据、不生成自动化脚本、不执行测试、不记录产品缺陷、不输出上线结论。
- 默认只在对话中输出评审结果，不写入任何报告，也不修改用例审核状态。
- 评审结论针对本次读取的用例版本；此前的评估结论、编写过程中的解释不能替代独立核对。

## 直接参考

- [资料处理规则](references/source-handling.md)：定位已有用例、核对需求依据、处理资料缺失和冲突时读取。
- [质量与可执行性评估](references/executability-evaluation.md)：评审标准、评分和准备难度分级。
- [输出模板](references/output-template.md)：在对话中呈现结果或经确认沉淀评审内容时读取。

## 流程

### 1. 确认评审对象与依据

读取用户指定的已有用例和相关需求资料。用户未指定文件，但当前工作区只有一个可唯一定位的目标时，直接采用；多个候选对象或版本无法区分时，请负责人确认，不自行创建用例文件。

默认评审整份文档；用户指定局部范围时仅评审该范围，并明确不能据此形成整份文档的结论。待审核用例也可以评审，不要求用例预先达标或已审核。

按资料处理规则核对文档范围、需求基准、已确认的覆盖方式和实现参考。资料缺失时，继续评审可判断的部分，并区分“用例本身缺项”与“评审资料不足”；不凭代码或经验补出正确预期。

### 2. 独立评审

先通读评审范围，再按质量与可执行性评估规则检查。每个问题指出用例编号或文档位置、实际内容、判断依据、影响和修改建议；没有编号时使用章节或行位置，不为评审而新增编号。

保留现有用例内容，评分只基于当前文档，不把建议中的修订视为已经完成。存在需求冲突或证据不足时记录限制，不为取得“达标”而改变范围或降低预期。

### 3. 在对话中输出并等待确认

按输出模板呈现质量结论及依据、可执行性汇总、问题清单和待确认事项。没有问题时明确写“无”，但不省略评审范围和资料限制。

本轮输出到此即完成评审；不自动优化用例、写回报告或继续复评。负责人补充资料或提供修订后的用例时，可以重新评审，明确本次采用的新版本与变化；用例修订不属于本 Skill。

### 4. 经负责人确认后沉淀

只有负责人明确确认具体评审内容并同意保存，或明确要求保存已呈现的评审结果后，才可写入。仅确认收到、要求修改或要求继续分析，不视为保存授权。

默认沉淀位置为本次评审的 `test-cases.md` 第 5 节“质量与执行评估”；负责人指定独立评审报告时采用其明确指定的位置，不擅自创建其他文件。按输出模板的保存规则执行，仅写入已确认内容。

保存前重新读取用例和目标报告。用例内容、需求基准或评审范围已变化时，旧结论不能直接写回；重新评审并请负责人确认。已有评审内容不得未经授权覆盖。

保存评审结论不等于用例审核通过；不修改“审核状态”、用例正文、需求基准、待确认问题或未覆盖说明。回复说明实际保存位置和内容范围。
