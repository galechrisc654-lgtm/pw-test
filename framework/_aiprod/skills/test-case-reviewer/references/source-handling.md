# 评审资料处理规则

## 评审对象

- 使用已有测试用例文档及用户指定的评审范围，不生成候选场景或新的用例。
- 记录文档路径或链接、版本线索及实际读取范围。只读取与当前评审相关的资料，不默认扫描历史用例、自动化资产、测试报告或缺陷。
- 不要求用例预先满足编写准入标准；文档不完整本身可以是评审发现。

## 资料角色

- **需求基准**：正式需求、验收标准、负责人明确确认的需求说明或正式产品规则，决定应有行为、范围和正确预期。
- **产品与交互参考**：辅助核对入口、控件、展示方式和相关已有行为；不能替代缺失的业务规则。
- **实现参考**：代码、diff、接口或数据库改动，仅用于核对描述中的实现入口和观察位置，不能证明预期正确，也不能独自扩大覆盖范围。
- **已有评审结果**：仅用于说明版本差异，不作为本次评分的依据。

范围覆盖按已确认的范围和覆盖方式判断。不因缺少与需求无关的性能、安全、兼容性或异常场景就判为遗漏；也不重新替负责人选择正向或负向覆盖方式。范围口径不明确时，请负责人确认。

## 缺失与冲突

- 用例缺少对象、主要动作、关键条件或可判定预期时，作为用例问题指出，不能通过推测补齐。
- 评审者未取得需求基准时，可以判断字段完整性、表达明确度、明显重复或矛盾，但不能声称覆盖完整、预期有依据或整份质量达标。
- 对无法判断的质量项注明“无法评估”及所需资料，不把评审资料不足等同于已证实的用例缺陷，也不把未知算作满足。关键质量项无法判断时暂不形成三档最终质量结论。
- 资料彼此冲突或代码与需求不一致时，列出各方内容、证据和受影响用例，请负责人确认；本 Skill 不修改需求口径或用例预期。
- 问题涉及代码时，在对应问题说明中直接引用源码 Git 仓库根目录相对路径，建议带行号；多仓库时注明仓库标识，不只提供机器绝对路径。
- 失效链接、缺失附件或无法识别的信息不自行还原。只对受影响的判断保留限制，不阻断无关部分的评审。
- 澄清优先提出不超过三个高影响问题，说明需要的资料及影响；用户不补充时交付限定范围的结果，不虚构评分依据。

## 执行准备与用例质量

未核实真实账号、环境、测试数据或工具是否就绪，不影响按文档要求判断准备难度，也不代表用例存在缺陷。缺少业务对象、关键条件或唯一预期属于质量问题；需要多账号配合、跨系统观察或模拟异常属于执行准备要求，两者分别报告。
