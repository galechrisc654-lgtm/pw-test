# API Contract Verification Rules

## 判断对象

验证对象是接口契约是否内部一致、可解释和可供调用，不是功能是否满足 PRD。需求文档和产品说明书可用于确定目标范围和理解术语，但不得作为接口真实路径、参数结构或响应结构的唯一依据。

## 可用证据

按当前可取得的证据组合判断：

1. 原始 OpenAPI：路径、方法、参数位置、请求体、响应、模型、鉴权声明和约束；
2. 接口提供方代码：Controller 路由与方法、请求/响应 DTO、序列化、字段校验、权限声明、统一响应包装和异常映射；
3. 接口消费者代码：前端或其他客户端的请求封装、参数构造、响应解包、字段使用、生成客户端和本地类型；
4. 中间与共享代码：网关路由或转换、共享 schema、公共 SDK 和跨仓库类型定义；
5. 非生产运行时：文档端点、OPTIONS/无副作用请求、明确授权的目标调用、实际状态码和响应形状；
6. 既有可信契约：相同指纹下已验证的登记项。

配置存在多个代码根目录时，必须逐个检查其中是否存在目标接口的提供、调用、转换或共享类型证据，并自行判断代码源角色；不要求配置人员预先建立映射。接口提供方通常决定服务实际暴露的协议，消费者代码用于确认真实调用方式和发现不兼容；两者不一致时不得为了迁就任一方静默改写契约，应结合运行时证据闭环，无法闭环则标记 `conflict`。

配置中的 commit 是代码校准基准，不自动表示测试环境部署事实。未明确提供其他版本线索时，默认先只读确认本地 `dev` 分支及其 commit，并以该分支版本作为代码校准基准；当前工作树不在 `dev` 时不得静默改用当前分支。只有用户明确提供其他 commit、标签或分支+时间，或已确认当前工作树就是 `dev` 基准时，才可采用相应模式；结论必须明确所采用的代码模式。

## 业务动作与技术接口

用户描述的“创建出库单”“提交审核”等是业务动作，不天然等于 OpenAPI 中名称相近的 operation。校准前先回答三个问题：

1. 动作要形成或改变哪些核心对象及必要关联对象；
2. 候选入口是完整业务入口、只处理局部对象的管理 CRUD，还是统一网关后的一个分发变体；
3. 请求数据经过哪个控制器、分发器、处理器和服务到达写入或外部调用边界。

接口摘要、方法名和 DTO 名只用于发现候选。候选接口的协议可以独立判为一致，但只有实现链能够完成用户所指动作时，才能把它映射为该业务动作。若主单、明细、附件或其他必要部分由不同调用完成，应明确这是多接口流程；若由统一入口在事务或编排中完成，应校准统一入口及其真实请求封装。

对候选接口做最低限度的业务合理性检查：结合产品资料、稳定领域概念和一般常识，判断接口输入与处理结果是否像一个完整的目标动作。例如“创建出库单”只接收和写入主单、完全没有商品明细，是继续追查的明确信号。业务常识用于发现候选接口与业务目标之间的缺口，并驱动 Agent 找到真正的业务目标入口；不能据此臆造字段、断定实现错误或直接修改契约。

候选接口只覆盖局部对象或触发上述疑点时，必须反向搜索其核心 Service、Handler 或写入方法的其他调用方，并检查统一分发注册，直到找到完整业务入口、确认由多个接口组成，或明确记录仍未闭环。

## 代码校准深度

OpenAPI 显式接口、文档遗漏接口和统一分发变体使用同一可信标准。根据接口复杂度检查以下方面：

1. **路由与暴露**：还原 HTTP 方法、外部路径、网关或全局前缀及注册条件，区分真实入口、内部方法和未激活处理器。
2. **输入与约束**：展开各位置参数和嵌套模型，并结合注解或手工校验、转换和条件分支确认真实可接受输入。
3. **处理映射**：追到足以确认协议语义的 handler 或服务边界；组合动作确认主从对象，统一入口确认分发键与处理器。
4. **输出与横切协议**：确认响应包装、主要失败形式，以及鉴权、租户、签名、幂等等实际调用要求。
5. **必要的交叉检查**：查看相关消费者、共享类型和相近入口，用于发现不一致或支持“没有其他入口”等排他性结论。

简单接口可以由少量文件完成判断；业务实现会改变输入或输出时，不能停留在 Controller 和 DTO。检查以能够解释如何构造有效请求、请求到达哪个处理边界、调用方会收到什么为止，不扩展为业务算法或需求符合性评审。证据记录关键代码路径或运行时观察即可，不要求逐项标签或固定数量。

代码可以成为主要契约证据，不强制执行有副作用的运行时调用。只有在声称“全部参数”“没有其他入口”或执行补充、移除等排他性结论时，才需要相应的反向搜索和暴露条件证据。示例请求只使用已有证据支持的值。

## 请求字段归因

请求契约以提供方实际接受与消费的字段、所有相关消费者实际发送的字段及可用运行时观察的并集为核对范围。消费者代码命中请求封装后，必须继续搜索其相关调用方和不同组装路径；存在表单对象整体提交、对象展开、动态合并或公共拦截器注入时，继续追踪字段来源。不得因首个调用路径已能成功构造请求就停止。

对影响调用说明或示例的字段，应区分：

- `服务端消费`：提供方直接读取并参与处理，注明必填或可选；
- `条件消费`：只在配置、请求类型或业务分支满足时读取，注明生效条件；
- `消费者透传`：消费者实际发送，但提供方业务模型不消费；只有序列化配置或运行时证据证明服务端接受时，才可作为可选字段写入契约，并明确其不影响当前处理语义；
- `框架或运行时补充`：由网关、拦截器、请求客户端或运行环境加入，注明位置和来源；
- `来源未明`：证据不足或相互冲突，不猜测字段用途或接受行为。

前端发送某字段不能单独证明服务端接受；DTO 未声明某字段也不能单独证明服务端拒绝。对于模型外字段，应检查实际反序列化、未知字段策略、请求转换层或非生产运行时结果。判定 `verified` 前，维护版中每个影响调用的字段都应有可复核来源和语义，相关消费者实际发送但未写入契约的字段也应有明确排除理由；否则使用 `blocked` 或 `conflict`。

## 源码版本定位

版本定位按仓库独立执行。同一个时间点可以在前端、后端、网关和共享代码仓库中得到不同 commit，这是正常结果，不得把一个仓库的 commit 套用到其他仓库。

按用户可提供的线索采用以下规则：

1. **Commit SHA**：用本地 Git 对象库解析为完整 commit，例如 `git rev-parse --verify "<sha>^{commit}"`。解析成功为 `confirmed`；对象不存在则为 `unknown`，不得用相近 SHA 替代。
2. **发布标签或构建版本**：先把输入作为本地 Git ref 解析。若构建版本不是 Git ref，只能使用仓库内或用户提供的权威“构建版本到 commit”映射；解析成功为 `confirmed`。不能解析时不得按名称或时间猜测。
3. **分支名 + 部署时间**：先确认分支或远端跟踪引用唯一存在，再以带时区的时间执行 `git rev-list -1 --before="<ISO 8601 时间>" "<分支引用>"`。所得 commit 为该引用在时间点之前的最近提交，置信度为 `inferred`，不是部署事实。
4. **只有部署时间**：只有在仓库的默认或部署引用能够唯一确定时，才可按上一规则给出候选 commit。若存在多个合理分支或引用，列出候选并标为 `unknown`，不得静默选择。时间没有时区时，先使用用户明确的环境时区；仍不能确定则要求补充或标记阻塞。

默认只使用本地已有 Git 对象和引用，不自动执行 `fetch`。需要远端缺失对象时，先报告缺口并取得用户授权。任何定位和读取都不得改变工作树、暂存区、当前分支或未提交改动；禁止使用 `checkout`、`switch`、`reset` 和 `pull`。

未提供其他版本线索时，先执行只读分支检查（例如 `git show-ref --verify refs/heads/dev`、`git rev-parse "dev^{commit}"`），确认 `refs/heads/dev` 存在；若本地没有 `dev`，仅当存在唯一的远端跟踪 `dev` 引用且对象已在本地时才可使用，并记录引用来源。`dev` 不存在、候选不唯一或目标代码只在其他分支可见时，版本置信度为 `unknown`，暂停依赖该仓库的校准判断，不得自行选择其他分支。当前分支不是 `dev` 时，使用 `git grep <pattern> dev -- <path>`、`git show dev:<path>` 等只读方式读取，不得切换工作树。

历史代码优先使用以下只读方式：

- `git ls-tree -r --name-only <commit>`：列出该版本文件；
- `git grep -n <pattern> <commit> -- <path>`：在该版本搜索；
- `git show <commit>:<path>`：读取该版本文件。

每个仓库都要记录：仓库路径、原始版本线索、解析出的完整 commit SHA、解析方式、置信度，以及适用时的分支、时间和时区。可将这组信息作为登记项的证据摘要，并在最终报告集中列出。

获得配置更新授权时，把最终定位结果写入对应 `code_roots` 项的 `commit`，字段格式以 `artifact-format.md` 为准。写入遵守以下约束：

- `id` 使用稳定的人类可读标识，`path` 必须是已配置或对话中明确提供的仓库路径；
- `commit` 只写本地已解析成功的完整 40 位 SHA；标签、构建版本、分支、时间、解析方法、置信度和自由文本证据不写入配置；
- 精确 SHA、可解析 Git 标签或权威构建映射可以直接形成配置值；分支加时间或单独时间得到的候选，必须由用户明确确认后才能作为固定代码基准写入；
- 无法唯一确定时不得更新该仓库配置，也不得覆盖既有 commit；应在报告中列出候选、置信度和解除条件。

`code_roots` 项没有 `commit` 时采用工作树模式：读取当前文件，包括未提交的相关修改；用 `git rev-parse HEAD` 记录基准 HEAD，用 `git status --short` 判断工作树状态。此模式不生成虚构 commit，也不得把 HEAD 当作工作树内容的完整标识。若工作树有相关未提交修改，证据必须标明 `working-tree-dirty`。

版本置信度影响状态判断：

- `confirmed` 表示版本线索已经可靠解析到 commit，但仍需代码内容与契约事实相互印证；
- `inferred` 表示 commit 只是时间与分支推导出的候选。用户未确认把它设为代码基准前，不得写入配置；
- `unknown` 表示无法唯一定位。若目标接口必须依赖该仓库才能判断，则标记 `blocked`；若运行时和候选代码互相矛盾，则标记 `conflict`。

## OpenAPI 覆盖缺口

代码存在 HTTP 入口但原始 OpenAPI 未收录时，先确认它是实际暴露入口、统一分发路径还是仅内部注册项。证据充分时按 `artifact-format.md` 写入 `openapi.supplement.json`，经构建器合并后进入 `operations.json` 和 `registry.json`；首次加入或契约变化时保持 `pending`，完成本规则的校准后才能设为 `verified`。

统一入口通过 `method`、`action`、命令码等字段分发时，一个 HTTP method + path 只保留一个 OpenAPI operation，请求体用 `oneOf` 或等价 schema 表达，并以 `x-api-contract-variants` 登记可独立绑定的业务变体。每个变体的 selector、请求模型、处理器和响应证据必须互相对应。

只有代码静态线索、无法确认运行时暴露、网关路径、序列化或完整请求结构时，不写确定补充契约；在交接中记录候选、缺口和解除条件。原始 OpenAPI 后续收录同一入口时，必须与补充契约显式对比和迁移，不能保留两个竞争定义。

实现文件存在但没有有效路由或分发证据时，不补成接口。若代码基准与测试环境部署版本无法对应，代码可以形成维护候选，但与运行时文档矛盾的部分不得直接判为已验证。

## 弃用与移除

- 仍可调用但已有提供方弃用依据时，保留 operation，设置 `deprecated: true` 和生命周期 `deprecated`。
- 有证据表明当前已不可路由时，才从维护版或补充契约移除，并同步为 `removed`。
- 文档未输出、消费者未使用或单次搜索未命中都不是移除证据；版本对应不清或强证据矛盾时使用 `blocked` 或 `conflict`。

原始快照始终保留。移除表达当前校准基准下不可调用，不表示历史上不存在。

## 状态判定

状态与等级分别表达“当前校准流程是否闭环”和“证据达到什么深度”。等级定义如下：

- `L0`：仅发现接口，尚不能确认结构；
- `L1`：路由、输入输出结构等静态契约已经对齐，但尚未形成完整可调用格式；
- `L2`：鉴权、参数位置、序列化和必要请求约束已经明确，可供测试或客户端调用；代码与消费者证据可以支持 L2，不强制真实调用；
- `L3`：在当前 fingerprint 和具体 request profile 下已有真实非生产运行证据。L3 只证明该调用契约，不等于业务需求正确或测试范围全部通过。

历史 `verified` 且未记录等级的接口按 L2 兼容。特殊线格式以 operation 下具名 `request_profiles` 维护，每个 profile 独立记录等级、证据和序列化规则；一个 profile 的 L3 不能外推到其他 profile。

API 测试执行不能自动升级等级。测试形成 Test Run 后，Agent 必须在独立的契约维护步骤中核对 `run-metadata.json` 的 Contract/部署快照、报告、当前 fingerprint、所用 profile 和请求响应证据，再调用 `api_contract_registry`；执行失败、关联不一致、报告缺失或对应关系不明确时不升级。

### `verified`

维护后的 OpenAPI 与适用的代码或运行时证据一致，且不存在影响调用的未决歧义。请求字段已按“请求字段归因”完成相关消费者调用路径核对和字段分类。记录足以复核主要结论的代码路径或观察；不要求固定证据数量，但“代码已检查”之类泛化说明不够。

### `pending`

接口为新增、发生指纹变化或尚未进入本次校准。它表示待处理，不表示存在问题。

### `blocked`

已经尝试校准，但缺少必要代码、环境访问、鉴权条件或语义证据，无法可靠判断。记录具体缺口和解除条件。

### `conflict`

两个或多个强证据对同一契约事实给出不兼容结论，例如运行时响应结构与当前代码声明不一致，且无法确认测试环境实际运行版本。记录冲突双方，不猜测哪一方正确。

如果生成文档明显错误，但代码或运行时证据足以确定真实契约，可以通过补丁修正后标为 `verified`；原始错误仍由快照和补丁保留。无法形成安全修正时才标为 `conflict`。

## 不在本 Skill 内判断

- 是否符合 PRD、产品说明书或业务预期；
- 业务流程、计算结果和数据状态是否正确；
- 测试用例是否通过；
- 是否允许发布；
- 是否应修改业务代码。

发现这些问题时只记录线索并转交相应的产品实现核查或测试流程，不得改变契约状态的定义。
